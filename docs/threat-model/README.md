# Threat model

Scope: Mode A connector deployment unless noted. "Test" names the automated check; "—" means the control is organizational and untestable from this repository.

| Attacker | Can reach | Intended controls | NOT prevented | Test |
|---|---|---|---|---|
| Malicious sender / prompt injector | Message content, attachments, HTML, headers | Sanitizer + sandboxed iframe; email treated as data; LLM has no send/forward/delete tool; action policy outside the model; draft post-checks; injection detector; sender-set headers never excuse failed authentication; flagged mail teaches nothing; per-message failure isolation; linear-time parsing | A convincing lure a user still acts on; novel phishing below thresholds; a user reading it in another client | `parser.test.ts`, `prompt-injection.test.ts`, `engine.test.ts`, `review-regressions.test.ts`, E2E hostile HTML |
| Stolen password / session | Victim's product account | Argon2id, TOTP, passkeys, hashed session tokens, revocation, rotation, rate limits, enumeration resistance; changing MFA or passkeys needs a current code, with limited attempts; adding any way in needs the password, or a sign-in through an identity provider in the last ten minutes, then ends other sessions and emails the owner; a code works once; account deletion needs the password and code | A stolen live session until it's revoked or expires, including one stolen within ten minutes of an identity provider sign-in; phished password without MFA, which can also add a factor. Someone with the password and session can still lock out the owner by enrolling an authenticator app; recovery codes help only if the owner already has them | `auth.test.ts`, `review-regressions-2.test.ts` |
| Attacker with someone's mailbox, or who can read reset and verify links | Links we email | Tokens hashed, single use, short lived; one live link per purpose; verify and reset each need a click on a page, so a mail scanner can't spend them; reset revokes every session, removes every passkey, and is blocked while TOTP is on unless a code is given | Someone in control of a mailbox can verify that address, and reset the password of an account with no authenticator app | `identity.test.ts` |
| Pre-hijacker: signs up with someone else's address and waits | That account, if the real owner ever shares it | Unverified accounts can't accept invitations. When the owner proves the address (reset, tenant SSO, SCIM adoption), a never-proven account loses its password, passkeys, identities and sessions | **A squatter who turns on TOTP blocks the owner's own password reset.** The address stays taken at sign-up until SSO, SCIM or an operator resolves it. Unverified accounts aren't expired | `identity.test.ts`, `sso.test.ts`, `scim.test.ts`, `saml.test.ts` |
| Account enumeration | Sign-in, reset, verify, SSO discovery | Same answer and timing path for every address on reset; discovery depends only on the domain; a made-up token fails like a used one | **Sign-up still says an address is taken**, a deliberate older decision. Whether a *domain* uses SSO is visible to anyone, since the next step is a redirect to its provider | `identity.test.ts`, `sso.test.ts` |
| Malicious or compromised identity provider | Any account on that tenant's verified domain | Sign-in limited to the exact domain the tenant verified by DNS; one tenant per domain; `email_verified` must be true; identities are scoped to one config and issuer, so changing issuer can't reuse them; an account with TOTP still needs its code; the DNS record is re-checked daily, and a domain whose record stays gone for 7 days stops being trusted and can be claimed by whoever proves it next | **Whoever controls a tenant's provider can sign in as anyone on its domain, including linking an existing account with personal mailboxes.** That's what SSO is. Configuring it is owner only for this reason. Someone who has lost a domain keeps this power for up to about 8 days, the grace period that stops a DNS mistake from cutting off a whole organization | `sso.test.ts`, `saml.test.ts` |
| Forged or replayed OIDC response | Callback | oauth4webapi: PKCE, nonce, state, issuer, audience, expiry, plus the signature against the provider's published keys. State is single use. The verifier and nonce are sealed under a cookie that never leaves the browser, which stops login CSRF | Provider bugs, stolen provider signing keys | `sso.test.ts` (fake provider with real JWTs), `identity.spec.ts` |
| Forged or replayed SAML response, signature wrapping | ACS endpoint, which takes cross-site POSTs | `@node-saml/node-saml`: signed assertions required. SP-initiated only: each response must answer a request this browser started, once. We check `Recipient` ourselves, because the library only warns. Wrapping variants tested | XML signature libraries have a history of bypasses, and this inherits any new ones: keep it patched. The binding cookie is SameSite=None, because the POST is cross-site; it's useless without its flow row | `saml.test.ts` |
| Account takeover by linking | Sign-in with Google or Microsoft | Never links to an existing account by email. Microsoft's plain `email` claim isn't trusted (nOAuth): it needs `xms_edov`. Separate client from mailbox authorization, identity scopes only | A person with an existing password account can't add Google to it yet, since there's no settings screen for it | `sso.test.ts` |
| SSRF through issuer URLs | Web process network | HTTPS only, ports 443 and 8443; the mail host guard's address rules; resolved once and pinned, certificate checked against the name; no redirects followed; 1 MB and 10 second limits. The SAML sign-in URL is never fetched, only sent to browsers | Egress must also be enforced at the network layer | `sso.test.ts` |
| Stolen or misused SCIM token | Membership in one tenant | Hashed, shown once, rotation ends the old one; rate limited per token and client; only domains that tenant verified; can't change an address; can't remove the last owner; only reaches people and memberships, never mail | A leaked token can add people to the tenant on its domains, and remove members, until it's rotated. The default role for those it adds comes from the SSO config | `scim.test.ts`, `identity-boundary.test.ts`, `identity.spec.ts` |
| Mail queue or dev outbox exposure | Rendered mail, which can hold a live link | Sealed under the KMS, row by row; jobs carry only an ID; wiped on handover or failure; logs carry only error codes. The dev outbox page returns 404 unless `DEMO_MODE=true`, and demo mode never uses a real relay | **`/dev/outbox` is public in demo mode**, including reset links, because demo mode has a public login anyway and must never hold real people | `identity.test.ts`, `mailer.test.ts` |
| Our invitations used for spam or phishing | Strangers' inboxes | Inviter must have a verified address; per-tenant and per-address limits; workspace names are stripped of links and control characters before they go in mail | A plausible-looking workspace name still reaches the recipient, in quotes. No bounce handling | `identity.test.ts` |
| Downgrade of the mail relay | Credentials and links in transit | TLS required unless the relay is on this machine; certificates verified; `TRANSACTIONAL_SMTP_URL` can't turn that off | What the relay does next. Mail to the recipient's server isn't under our control | `mailer.test.ts` |
| Notification content leaking | Admins, grantees, mail logs | Rows hold a kind and an ID, and go only to the mailbox's owner; RLS keeps them to that person; digests have counts only and go only to verified addresses | That something was held, and when, is visible to whoever reads the owner's digest mail | `notifications.test.ts`, `identity-boundary.test.ts` |
| Stolen OAuth token (from outside us) | Victim's provider mailbox directly | Provider-side controls; we detect `invalid_grant` and stop | Anything at the provider | `sync-send.test.ts`, `gmail-slice.test.ts` |
| Compromised device / extension | Everything the user sees in the browser | Short sessions, session list, CSP, HttpOnly cookies | An extension reading the DOM; a compromised OS | — |
| Insider with support/dashboard access | Admin UI | No content endpoint exists; admin console reads aggregates only; audit log | See "privileged operator" | `admin-cannot-read.test.ts` |
| DB / snapshot / object-store exposure | Ciphertext, metadata, **plaintext tsvector** | Envelope encryption, HMAC sender identifiers, root key outside DB | Search lexemes and timing/volume metadata are exposed from a dump. Disable server search to remove lexemes | `crypto.test.ts`, `at-rest.test.ts` |
| Database backup | Everything in it | Content is sealed, proven by `restore-drill.test.ts`, which finds a message's words only in the disclosed search index | With the root key, a backup is fully readable, and a backup from before a deletion keeps deleted data until it expires. Root key held apart, short expiry |
| A restore bringing deleted data back | Accounts, mailboxes, sealed bodies, retained and opted-out data | Each erasure writes an outbox row in its own transaction, shipped by the worker to a content-free, hash-chained log; `pnpm restore:reapply` replays it through the live erasure code before anyone reaches the database; a production worker won't boot without a log | The backup file itself stays readable until it expires: this restores deletions on restore, and doesn't reach into a backup. A log on the database's own storage dies with it. Losing the database between commit and ship loses that entry | `restore-drill.test.ts`, `deletion-log.test.ts` |
| Tampering with the deletion log | Forged lines erasing someone's data, or removed lines bringing it back | Hash chain, checked before anything's applied; checked against the shipped rows the restored database holds, and the head in the worker's logs; ids and tenant contexts keep a replay inside the tenant a line names | The hashes aren't keyed, so someone who can write to the log can rewrite it from some point on, and whole lines cut from the end look clean unless a witness knew about them. `--allow-broken-chain` trusts any line whose own hash holds | `restore-drill.test.ts` |
| The deletion log itself leaking | Which accounts and messages were erased, and when | Allowlist of ids, a kind and a time, enforced when written and read; no content columns; private file; web process has no access | Ids and timing remain. An erased account's id in the log can be matched to a backup, by someone who has both | `deletion-log.test.ts` |
| Embedding vectors from a dump | Sealed vectors | Envelope per record, AAD bound; never plaintext, no pgvector | A deployment with `AEGIS_EMBEDDINGS=local` holds decrypted vectors in memory during a search. A vector's size and existence say that a message was indexed | `semantic-search.test.ts` |
| Compromised build/deploy pipeline | Production code | Lockfile, SBOM, secret scan, signing steps in CI (`.github/workflows`) | A malicious build that passes CI; **not prevented in Mode A or B** | — (CI config, not exercised here) |
| Privileged operator with deploy rights | Production memory, KMS use | Separation of duties, JIT access, audit | **Can read mail in Mode A**. Stated in Privacy Center | — |
| Cross-tenant query bug | Other tenants' rows | RLS under non-superuser role as defense in depth, authorization at the service layer, 404 on foreign IDs | A bug in `withSystem` paths; a static test restricts those. **SQL injection isn't covered by RLS:** a role can set its own `app.user_id`, so arbitrary SQL in a request context could impersonate a user. All SQL is parameterized; search input is reduced to word characters | `tenant-isolation.test.ts`, `process-boundary.test.ts` |
| Malicious model provider / AI output | Prompts when hosted AI is on | Off by default; per-user consent; output schema validation; post-generation checks; output treated as untrusted and rendered as text | Provider retention beyond contract; a model reading content it was sent | `prompt-injection.test.ts`, `ai.test.ts` |
| Platform operator, or a stolen operator session | Tenant metadata, suspension | `aegis_operator` has no table grants; definer functions with column-level grants that exclude content; the session must have presented a second factor, not just belong to an account that has one; append-only log the tenant can partly see | Someone with deploy rights or database superuser isn't constrained by this. See `docs/runbooks/operators.md` | `operator-roles.test.ts` |
| Hosting provider / TEE adversaries | Host memory, disks | Encryption at rest and in transit; Mode C not built | Host-level plaintext capture during processing | — |
| Accidental personal/work crossover | User error | Sending identity always shown; server compares expected identity to account; account chips on rows | User picking the wrong account deliberately | `sync-send.test.ts` |
| SSRF via mail settings | Worker network | Host guard denies private, loopback, link-local, metadata ranges; resolves and pins IP; port allowlist | Egress must also be enforced at network layer in deployment | `ssrf.test.ts` |
| Hostile MIME / archive bomb | Parser CPU and memory | Size caps; part limits; zip central-directory inspection without decompression; timeouts | Parser 0-days in dependencies | `parser.test.ts`, `engine.test.ts` |
| Poisoning via feedback or relationship graph | Priority and detector inputs | Relationship is evidence, not trust; sender-driven signals are bounded; allowlist can't override malware; feedback is per-user | A patient attacker building real correspondence history | `stories.test.ts`, `engine.test.ts` |

## Independent review
An adversarial review on 2026-11-06 (read-only, with working proofs) found 16 issues and no cross-tenant or admin read path. All are fixed and replayed in `review-regressions.test.ts`, except as noted in `docs/STATUS.md`. This was an internal review, not a substitute for an external pen test.

## Declared limits
0. RLS context variables are set by the same connection they protect against. RLS stops logic bugs, not arbitrary SQL execution. The process boundary still holds: a web login can't read credentials or become the worker.
1. Origin providers (Gmail, Outlook, iCloud, …) retain their own access to mail.
2. Connector-mode quarantine happens **after** provider delivery. A user can open the message in another client before or after analysis.
3. Detection metrics in this repository are measured on a **synthetic corpus only** and say nothing about field performance.
4. No external penetration test or cryptographic review has been performed.

5. Nothing in the identity work has been tested against a real identity provider, Google, Microsoft, or a real SMTP relay. Fakes speak the protocols and real libraries are on our side of them, but what real providers actually send is unverified: `docs/STATUS.md` lists what to check.
6. If an identity provider goes down while SSO is required, nobody on that domain can sign in until it's back or an operator clears the flag. There's no break-glass account. Requiring it needs one successful sign-in first, so a typo can't cause this.
